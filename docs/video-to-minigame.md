# 玩法视频 → 微信试玩小游戏：制作流程

把一条玩法成片（通常是 AI 写实版工程渲出来的广告视频）做成可以玩的微信小游戏试玩。本文是流程和标准，踩过的坑在 [lessons.md](lessons.md)。
做过的：[瀑布捞鱼](../games/waterfall-fishing/README.md)（2026-11，源工程 `20261027_Township换皮_V17写实`，写实合成管线 `web/real.js`）、[水下巨木](../games/underwater-log/README.md)（2026-11-25，源工程 `水下巨木_写实投影版工程_V20`，写实投影管线 `web/k57/real57.js`）。两个源工程的写实做法不一样，烘焙脚本要按源工程改，但思路相同（见第 4 步）。

> 每做完一个游戏，按 [AGENTS.md](../AGENTS.md) 的「迭代规则」回来改这份文档：哪一步不对就改哪一步，别只在末尾追加。

## 输入（开工前先问清 / 找齐）

| 输入 | 例子 | 用来做什么 |
|---|---|---|
| 成片 | `<源工程>/最终成片/*.mp4` | 定玩法节拍、镜头、画面目标 |
| 源工程 | `D:/AI 3D 写实版 工程/<工程名>/`（Three.js 场景 + 写实合成管线 + FBX 模型 + 贴图） | 美术资源的唯一来源，环境底图从它烘出来 |
| 已有成品 | `shared/playable/`、`games/*/`（[瀑布捞鱼](../games/waterfall-fishing/README.md)、[水下巨木](../games/underwater-log/README.md)） | 试玩外壳的唯一标准（引导、自动玩、品牌、强制结束、按钮、HUD、埋点）和能直接复用的资产、代码 |
| 风格要求 | 「写实」 | 最终画面必须和成片一个质感，不能是卡通 |

源工程只读，绝不改它。抽的帧放 `_ref/`（不进仓库）对着看。
开工先列一遍「成品里已经有的」：同一套模型（巴斯特、Q 版顾客）、音效、logo、外壳、脚本，能拿的直接拿，只做新的部分。

## 第 1 步：看片，写节拍表

1. 抽帧：`ffmpeg -i 成片.mp4 -vf fps=1 _ref/film/f_%02d.jpg`，再在关键动作附近加密抽。
2. 写一张节拍表：时间 → 镜头 → 主角在干什么 → 屏幕上出了什么（数字、地块、按钮）→ **配角在干什么**（顾客推栏、拍栏、举手催、拿到货欢呼；厨师切菜）。配角站着不动用户会指出来，**画面里的人群也算**（不能只做前排）；这些动作源工程里通常有现成代码（瀑布捞鱼：`web/custactions.js`）。
3. 从节拍表里找出**核心循环**（瀑布捞鱼：捕鱼 → 交给加工台 → 拿货 → 卖货 → 收钱 → 买地块）和**升级节点**（雇工、传送带、售货员）。成片里一闪而过的东西只做装饰，不做成玩法。
4. 定试玩时长：自动玩从开局到最后一次解锁约 55–60 秒，满 90 秒强制结束。

## 第 2 步：搭工程（照 `games/waterfall-fishing/` 的结构）

```
games/<名字>/
  minigame/   game.js（先建上屏画布）、game.json、project.config.json、index.html（浏览器调试）、assets/
  src/        main.js 入口
  tools/      这个游戏专用的烘焙 / 压缩脚本
  README.md   玩法、画面做法、重新烘焙步骤
```

共用模块在 `shared/playable/`，游戏里按相对路径 import（`../../../shared/playable/xxx.js`），esbuild 打进同一个包：

| 模块 | 内容 |
|---|---|
| `adapter.js` | 微信环境的 polyfill：TextDecoder、AbortController、`self`、navigator、performance |
| `platform.js` | 微信 / 浏览器的差异：画布、触摸、图片和二进制读取、音频、安全区和胶囊位置、埋点 `report`、`gameEnd`、`download` |
| `ui.js` | 精灵图集 + 一次合批画完的 2D 界面（logo、立即体验、轻划移动、摇杆、数字、订单气泡、表情）。`buildAtlas({ …, renderer, bubIcon, extra })`：气泡图标、游戏自己的精灵从参数传。没有「我来操作！」 |
| `audio.js`、`loader.js`、`util.js` | 音效 / 背景音、带进度的资源加载、数学小工具 |

还没抽出来、从已有游戏复制改的：`main.js` 的流程部分（加载页、自动玩和接管、强制结束、`?speed` / `?zoom` / `?debug` / `?raf=timer`、固定步长追帧）、`world.js`（底图 + 深度的环境渲染、阴影、写实调色）、`items.js`（实例化物品 + 栈）、`fx.js`（地块、圆圈、箭头路、闪光）。
人群和配角动作：瀑布捞鱼的 `custactions.js`（Bip001 骨骼的程序化动作）、`crowdacts.js` 和水下巨木的 `crowd.js`（人群的骨骼动画烘成姿势帧、实例化画，每个人按自己的相位分到对应帧）。

## 第 3 步：试玩外壳（所有游戏统一）

直接用 `shared/playable/` 和已有游戏的 `main.js` 流程（它们就是标准），规则：

- 开局直接自动玩；**自动玩期间一律显示「轻划移动」和滑动手势**（不只是第一次）。
- 任意处按下就是摇杆原点（拖动 80 封顶，10 以内不动）；松手 2 秒后恢复自动玩。
- **没有「我来操作！」按钮。**
- **「立即体验」在左上 logo 下和结束页都显示，微信里也显示。**
- 最后一次解锁后 2.4 秒，或满 90 秒，强制结束：画面压暗，显示大 logo。微信里调用 `wx.notifyMiniProgramPlayableStatus({ isEnd: true })`。
- 埋点 `wx.reportGameEvent` 的编号和已有游戏一致：1001 启动、1003 首帧、1004/2001 首次触摸、1011/1013 结束、1012 点立即体验。
- 微信里，右上角胶囊菜单下面才放 HUD，顶部按安全区让开刘海（`sysInfo().menu`、`safeTop`）。

## 第 4 步：写实画面

目标：画面和成片一个质感，同时小游戏包要小于 4 MB、能跑 60 帧。做法是**环境烘成图，会动的东西才用 3D**。

### 环境：从源工程烘一张写实底图

1. 在源工程的写实管线里，放一台**远处、近正交、俯角和偏航与成片相同**的相机（D=3000），用 `setViewOffset` 分块渲出整个可玩区域。
   - 烘焙页放在源工程 web 目录「里面」（`tools/serve.mjs` 把 `/web/bake_*` 映射到游戏的 `tools/bake/`），复制一份源工程入口（如 `scene57.js`）多挂一个 `window.placeAt`。
   - **用无头浏览器跑，不要在浏览器窗格里手敲**：`games/underwater-log/tools/bake/run.mjs`（puppeteer-core 直接用源工程 `node_modules` 里那份，浏览器用本机 Edge）打开烘焙页、执行 `tools/bake/steps/*.js`，一步约 20 秒，可重复。
   - 源工程自己有「哪些是静止环境」的分类就直接用（real57 的 `REAL_LISTS.ENV / HIDE_B`），别自己再写一套；会动的全藏掉（A = B，合成结果就是纯投影），自带写实材质的会动物体（冰洞的水）留着照常画。
   - 合成着色器按成片相机距离选单帧图 mip，远处相机要改成按每米像素算（`patchLod`），不然底图是糊的。
   - 取景框：营地（主角能去的范围）外扩半个手机画面（横 5.6 米、竖 10 米），ppm 64–72。
2. 产出：一张写实颜色图（瀑布捞鱼 1656×2592 / 72 像素每米，水下巨木 1592×1992 / 64），一张 16 位深度图（B 通道标出水面），有流水的再加一张流向图。
3. **再烘一张覆盖度图**（real57 是 `realdbg=1`：白 = 写实单帧图拍到了，品红 = 哪张都没拍到、只有兜底颜色表的卡通色）。用它量出镜头能取景的范围写进 `meta.clamp`（游戏 `setView` 不拍出去，太高的屏幕横向少看一点），没拍到的小块用附近的写实像素补（`fixenv.py`）。瀑布捞鱼是对着成片目测补树；有覆盖度图就不用猜。
   覆盖度图外面的颜色压糊、深度压成常数，包能小 200 KB 以上。
4. **烘完对照成片找缺的东西。** 源工程里会动、会变的物体（逐根摆的栅栏、柜台后排会晃的木桩、解锁前后换样子的柜台、研磨机、巨木）烘焙时被藏掉，底图里就没有，先用分类列表（`steps/list.js`）列出来逐个决定。补回来的 3D 物体颜色：
   - 底图里有**同一个模型、同一个朝向**的同款（柜台 2 ↔ 柜台 1）：材质直接按「挪到同款位置后的世界坐标 → 烘焙相机投影 → 底图 UV」取色（`props.js` 的 `envUVMat`）。游戏相机和烘焙相机同一个朝向，看得见的面在同款身上都看得见，和底图完全一样；锁着的灰色版本在同一张图上去饱和、调色。
   - 形状不一样的：用 UV 空间烘的写实固有色（下一节）。
5. 游戏里的相机**就是烘焙相机**，只用 `setViewOffset` 平移取景。环境用一个全屏三角形画出来并写 `gl_FragDepth`，这样人和栅栏、柜台之间的前后遮挡是逐像素正确的。水面深度往下压一点（0.55 米），水下的东西才看得见。
6. **整体调色比成片亮一点、艳一点**：成片的亮度做到小游戏里，手机上看着暗沉（水下巨木和成片亮度、饱和度量出来一样，用户还是嫌暗）。底图和会动的东西过同一套调色（sRGB 里：增益、中间调伽马 < 1、饱和度、对比，水下巨木 `world.js` 的 `uGr`，`?gr=` 调），暗角压轻。
7. 动起来的环境：水面细节沿流向图分两相交替流动；会动物体的阴影用自己的深度阴影图投到底图上；最后统一加颗粒和暗角。

### 人物和道具：原模型 + 烘好的颜色贴图

1. 几何、骨骼、动画用源工程的 GLB / FBX；颜色在 UV 空间烘：拿场景里**已经套上源工程写实材质**的网格（水下巨木的 `real_mat57.js` 按物体坐标叠噪声、卷树皮也照样烘得出来），把材质链在 UV 空间渲一遍存成颜色贴图（每次烘焙用不同的 program cache key，否则会拿到上一次的结果）。见 `games/underwater-log/tools/bake/bake_props.js`。
   源工程 GLB 里的材质名可能是乱码（浏览器里认不出中文名），按源工程自己的材质分类函数（`catOfDbg`）或场景对象（`JM.woodpile`）找网格。
2. **烘完逐张打开人物、道具贴图看**：大片均匀的灰色说明没烘到（会显示成白模）。模型只占源图集一小块时，也可以直接从图集按 UV 框裁（`tex.py` 的 `atlas_crop`）。
3. 用 gltf-transform 压缩（`tools/assets.mjs`）：去掉嵌入贴图、描边壳（`描边` 材质）、切线和第二套 UV（没有法线贴图用不上，主角省 80 KB）、weld、dedup、按需 simplify、动画 resample、删掉没用的动画通道和没用到的片段、quantize。动作分在几个 GLB 里的按骨骼名并进来（源工程 rotOnly 的只留旋转和根骨位移）。**主角保留原始网格和手指动画**，配角和道具才减面；几百人的人群另出一档更低的（水下巨木：顾客 2264 面、人群 946 面）。
   道具归一（长边、最薄的轴朝上、底面中心到原点）照源工程 manifest 的 targetLength / targetHeight，别靠目测；最薄的轴不朝上，肉和钞票会立着。
   **蒙皮模型先看源工程加载时有没有修过**（`assets.js` 的 `fixSkinWeights` 这类）：有就把那段原样搬进游戏、加载时跑，处理过的 GLB 上修出来的顶点数要和源工程一样，不一样就是打包步骤改了权重（quantize 会）。循环段（manifest 的 `loops`）在打包时裁，不在游戏里 `trim`。
   人物做完拉近看定格姿势表（`?pose=<动作>&pt=<秒>` 定住姿势，每个动作取 4 个时刻拼一张），手、帽子、背带、袖口有没有炸开。
4. 给会动的东西套上成片的写实调色（饱和度 0.62、亮度 0.85、色偏 (1.03, 1, 0.94)），和底图融在一起。
5. 贴图开重复采样（RepeatWrapping）：原模型的 UV 常常超出 0–1。

## 第 5 步：玩法实现

- 场景布局沿用源工程的世界坐标（米）。底图是按这套坐标烘的，坐标一致，深度遮挡才对。
- 可走区域、碰撞、交互点、数值全部放在 `config.js`（`L` 是布局，`T` 是数值）。走的范围用烘焙深度图量，不要目测。
- AI 自动玩要能从任何状态继续：玩家中途接管，把主角丢在哪里，自动玩都要能接着走完流程。
- AI 目标要有「做完再走」的规则，不然会来回跑：背着东西还没满、站在取货点就接着拿；到了柜台就放完再走；柜台这边还有人在吃、钱还在飞就等着收完；往柜台走了就别回头。
- 调数值时记每次换目标（`G.log`：时间、目标、背着几个、钱、库存），`?speed=3` 跑一遍就知道时间花在哪：瓶颈常在流水线某一段的上限（水下巨木：送柴带「在路上的」上限让烤炉断柴，堆满了木头也送不过去）。
- 人物姿势跟状态走：手里有东西才做搬运姿势；背上的东西贴着背；水里身体前倾，像在游泳。
- **背的东西放在主角身子外面**：先量主角蒙皮以后的轮廓（各动作取几帧，腰到头往后最远到哪），每摞靠身子的那一边放在它外面，摞的中心再往后让半个进深；垒起来要直，只有钞票柱留一点弹性。交付前数一遍「落在背的东西里面的主角顶点」，要是 0。
- **同时背两样（货和钞票）时，两摞在背后左右并排**：背点不动，两样都有时并排系数用 0.1 秒缓到 1，两摞转成前后放，按两样东西的实际宽度左右排开、中间留 6 厘米、往后让出长出来的半截（别照抄示例的 0.27 米，它的鱼和我们的肉尺寸不一样）；太长转不了的（1 米的木头），钞票摞在它后面。只有一样时就在背后正中。见水下巨木 `game.js` 的 `side`。

## 第 6 步：验证（交付前必做）

1. 浏览器：`node tools/serve.mjs`，打开 `/games/<名字>/index.html?speed=3&debug=1`，看控制台的 `[flow]` 日志，确认自动玩能一路走到结束，记下每次解锁的时间。
2. 截图逐帧看：开局、每个交互点、每次解锁、结束页。重点看手、背上的东西、水里的姿势、物体是否穿模、引导圈是否闪烁、底图边缘有没有露馅、**堆起来的东西（钞票、货）在正常镜头下有没有被挡**、配角是不是在动。
   定格截图：在页面里等到想要的状态（例如 `__dbg.GM.state().strip.n >= 10`）就设 `__dbg.paused = true`，需要时用 `__dbg.look = [x, y, z]` 把镜头挪过去。
   窗格没显示时浏览器不触发 `requestAnimationFrame`，加 `?raf=timer` 用定时器跑主循环；窗格藏起来时画布也不渲染，截图用 `node tools/shot.mjs <名字> "<网址参数>" "<等待条件>" <输出> [张数]`（无头 Edge，等到条件成立定格截画布）；输出写 `--eval` 就是在页面里跑那段 JS、打印结果（量尺寸、数穿模）。性能：直接在页面里给 `GM.update`、`world.render` 计时，或看微信开发者工具里的 fps。
3. 微信开发者工具：MCP 不可用时用命令行，`node tools/wxide.mjs <工具名> --project <绝对路径>/games/<名字>/minigame …`（直接把参数数组交给开发者工具的 Electron，不经过 cmd，JS 源码里的引号不会被拆坏）。`open_project_window` 打开、`simulator_screenshot` 截图、`simulator_refresh` 重新编译、`automation_game_action` 模拟滑动、`close_project_window` 关掉（移动文件前）。
   `automation_evaluate` 跑在另一个 JS 上下文里，读不到游戏的 `GameGlobal.__dbg`；`get_simulator_console` 在模拟器窗口模式下常常是空的。要看微信里的 fps 和报错，用 `node tools/build.mjs <名字> --dbg` 打一个带状态浮层的包，截图放大左下角看，看完重新正常打包。
4. 包大小：`minigame/` 去掉 `index.html` 要小于 4 MB（4194304 字节）。超了先看 `tools/glbsize.mjs` 哪个属性占地方（切线、第二套 UV、没用到的动画片段最常见），再看底图取景范围外的部分。
5. 在报告里写清楚**没有验证的部分**（真机、声音有没有用耳朵听过）。
