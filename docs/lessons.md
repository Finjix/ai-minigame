# 经验库

每个小游戏做完后都往这里补。格式：**现象 → 原因 → 做法**，后面注明出自哪个游戏、代码在哪。
同一个坑第二次出现时，不要再加一条，而是把它提到 [video-to-minigame.md](video-to-minigame.md) 的对应步骤里，变成默认做法。

## 一、用户会盯着看的地方（交付前自己先查）

瀑布捞鱼交付后，用户反馈的问题几乎全是**看截图就能发现的细节**。下面每一条都是用户实际指出的，下次交付前逐条自查：

| 自查项 | 瀑布捞鱼里用户指出的问题 | 做法 |

| 引导圈会不会闪 | 开局指向湖里的圈一直在闪 | 圈的目标改成固定点 `FISH_SPOT`，不要跟着最近的鱼跳；圈的 key 不随鱼的位置变（`game.js`、`fx.js`） |
| 空手时的姿势 | 手里没东西也往前举着 | 只有手里拿着货才播搬运姿势 |
| 手和货的位置 | 手举得比货还高 | 货堆跟着手腕骨骼（Wrist_L/Wrist_R）走：`chars.js` 的 `hands()`、`game.js` 的 `holdBase`/`updateHold` |

## 二、技术坑

### 微信小游戏环境

- **画面是黑的 / 画到了离屏画布上**：微信里第一次调用 `wx.createCanvas()` 返回的才是上屏画布。在 `minigame/game.js` 里最先建它，存成 `GameGlobal.__mainCanvas`，再 `require` 打包文件。
- **`AbortController is not defined`**：Three.js 的加载器会用到。在 `adapter.js` 里补上（还有 TextDecoder、`self`、navigator、performance）。
- **WebGL2**：用 `canvas.getContext('webgl2')` 拿到 context，再以 `{ canvas, context }` 传给 `WebGLRenderer`。
- **GLB 加载**：读成 ArrayBuffer，交给 `GLTFLoader.parse`。GLB 里不嵌贴图，贴图单独用 jpg 加载。
- **打包**：esbuild 打成一个 IIFE，target 设成 es2018。

### 模型和贴图

- **压缩过的 GLB，节点位置不对**：gltf-transform 的 quantize 会把缩放、平移写到节点上，直接拿 geometry 就丢了。用 `items.js` 的 `bakedGeo` 把节点变换烘进几何体，并做反量化。
- **白毛、胡子变黑**：原模型有一半 UV 在 U 1–2 之间（UE 默认重复采样），贴图用夹边会采到边缘的深色。人物和道具贴图一律用 RepeatWrapping。
- **烘出来的贴图都一样**：在 UV 空间烘材质时，每次烘焙要用不同的 program cache key，否则 Three.js 会复用上一次的着色器。
- **厨师是白模（灰白一片）**：`bake_chars.js` 的 `uvRemap`（模型只占图集一小块时，把那块拉满整张贴图）算了裁剪框却没在顶点着色器里用，只烘到角上一小块，`tex.py` 再把空白处用均色填满。已修烘焙脚本（未重跑），游戏里的厨师贴图改成直接从源工程图集按 UV 框裁（`tex.py` 的 `atlas_crop`，颜色按 UE 材质乘 1.5）。烘完要逐张打开贴图看。
- **gltf-transform 的 `prune` 会删掉属性**：要设置保留属性，并清掉 extras。

### 画面

- **2D 界面不显示**：界面四边形被背面剔除了，材质设成 `side: DoubleSide`。
- **界面几何体的包围球是 NaN**：手动设置包围球，不要让 Three.js 自己算。
- **水下的东西看不见**：底图写深度时，把水面压低 0.55 米。
- **阴影把雪花也画进去了**：阴影 pass 里隐藏 Points。
- **深度量化**：16 位深度按 4 的步长量化（约 1.8 厘米），PNG 能压得更小，精度也够用。
- **底图里少了成片里有的东西**：源工程里会动的物体（逐根摆的栅栏圆木，被推时闪红、晃）在烘焙时归为 moved 被藏掉，底图里就没有了。补回来时不另外画颜色：新物体上每个点换算成底图里**同款、没被藏的物体**上相同相对位置的点，用烘焙相机投影取色（`fence.js`，`world.js` 的 `BAKE_VP`）。参考物体要选背后不是水、顶上没积雪、和要补的那段颜色接得上的；采样往中心收 10%，边上才不会采到背后的东西。先在参考物体原位放一根（`?fencedbg=1`），看不出来就是对齐了。
- **几百人的人群要做动作**：动作烘成每帧一个静态几何体，每个「动作 × 帧」一个实例化网格，每帧按排程把人分进去、设 `count`；静态人群里对应的人矩阵缩成 0。蒙皮用 `SkinnedMesh.getVertexPosition`，法线用 `applyBoneTransform` 传 w=0 的 Vector4。瀑布捞鱼 156 人、约三成同时在动，多 40 个网格，逻辑一步 0.38 ms。
- **两个材质用了同一份着色器**：`realLook` 设了 `customProgramCacheKey`，后加的 `onBeforeCompile`（熟肉的焦条）不改键，three 拿键相同的另一个材质的程序，焦条时有时没有。每加一层 `onBeforeCompile` 都要把键也加一段。
- **量化过的 GLB 改蒙皮权重按坐标挑顶点，挑不到**：顶点存的是归一化整数，反量化矩阵在网格节点上；先乘 `mesh.matrix` 再比坐标（伸缩磨臂）。
- **底图有兜底卡通色**：投影类写实管线（real57）在单帧图没拍到的地方用颜色表兜底，看起来是平涂的卡通色。烘一张覆盖度图，按它定镜头范围和要补的地方（`fixenv.py`）。
- **程序化骨骼动作很慢**：源工程的 `rotC` 每转一根骨头都 `updateMatrixWorld(true)` 刷新整棵子树，11 个人在 3 倍速下帧率掉一半。只用 `getWorldQuaternion` 沿父链往上算就够了（`custactions.js`）。

### 自动玩和数值（水下巨木）

- **主角拿到第一根木头就跑去添柴、在柜台放一块肉就回托盘**：目标只看「手上有什么」，没有「做完再走」。加规则：站在取货点、没满、还有货就接着拿；在柜台前就放完；这边还有人在吃、钱还在飞就等着收；往柜台走了就别回头（`game.js` 的 `chooseTarget`）。
- **第一轮卖完钱不够买第一个地块**：6 块肉，柜台前只有 5 个人在等，第 6 块要等补位的人走过来，主角先走了。第一个地块价格要按「第一轮必然能拿到的钱」定，并让主角在柜台等钱收完。
- **送柴带开了反而更慢**：「在路上的木头 + 炉里的柴 < 8」这个上限让烤炉一直断柴，木材堆是满的也送不过去。上限放到 14。查瓶颈：每秒记一次各段库存（木材堆、炉柴、带上、托盘），哪段一直满、下一段一直空，就是卡在中间。

### 本机环境（Windows）

- **`git mv` 报权限错误**：微信开发者工具和本地服务开着时会锁住文件。先 `close_project_window`、停掉预览服务，再移动。
- **Bash 里 `python - <<'X' … X` 偶尔报「unexpected EOF while looking for matching `''」**：内容里有三引号、反引号混在一起时会出这个错（引号成对也会）。长一点的改代码脚本先用 Write 写成文件再 `python -I 文件` 跑。
- **调微信开发者工具命令行，JS 源码参数被拆坏**（`Invalid or unexpected token`）：`wechatide.cmd` 经过 cmd.exe。用 `tools/wxide.mjs`（参数数组直接交给它的 Electron）。
- **烘焙要用 Chrome，本机只有 Edge**：puppeteer-core 的 `executablePath` 指 Edge（`C:/Program Files (x86)/Microsoft/Edge/Application/msedge.exe`）就行。puppeteer-core 用源工程 `node_modules` 里那份，入口是 `lib/puppeteer/puppeteer-core.js`。
- Python 脚本都加 `-I` 运行。

## 三、流程上的经验

- **先把试玩外壳跑通，再磨画面。** 自动玩能从头走到结束以后，后面每次改动都能用 `?speed=3` 快速回归。
- **每次改完都截图看，并对着用户的截图找同一个位置。** 用户发来的截图就是验收标准。
- **用户的一句话可能是全局规则。** 「后面版本的游戏都不需要这个」这样的话，要写进 [AGENTS.md](../AGENTS.md) 的定稿规则，不能只改当前游戏。
- **表述有歧义时，说出你的理解再动手。** 比如用户说「增大一下视距，现在镜头拉太远了」，实际意思是把镜头拉近；动手前先说明自己是这样理解的。
- **调试开关要从第一天就有**：`?speed=`（加速）、`?zoom=`（远近）、`?debug=1`（错误浮层 + 状态）、`window.__dbg`（控制台里读状态）、`[flow]` 日志（首帧、解锁、结束的时间）。
- **定格截图**：`__dbg.paused = true` 定住游戏，`__dbg.look = [x, y, z]` 把镜头挪到指定点。先用一段脚本等到某个状态（例如 `__dbg.GM.state().strip.n >= 10`）再定格，比盲等截图准。
- **浏览器窗格没显示时 `requestAnimationFrame` 会降频甚至完全不触发**，自动玩跑不起来、fps 读数也不准：加 `?raf=timer` 改用定时器驱动主循环。要看性能，在页面里直接计时 `GM.update` 和 `world.render`（看 `renderer.info.render` 的 calls / triangles），或者看微信开发者工具里的 fps。只手动调 `GM.update` 推进不走 `updateFlow`，解锁时间会偏，不能拿来验流程。
- **成片里的配角小动作也是验收内容。** 写节拍表时就要记下配角在干什么（顾客推栏、拍栏、举手、欢呼），源工程里通常有现成的动作代码可以移植。
